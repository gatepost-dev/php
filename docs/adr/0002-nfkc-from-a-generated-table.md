# Apply NFKC from a generated table, not from ext-intl

The grammar applies Unicode NFKC before it checks a code. PHP has NFKC only in ext-intl, which many WordPress hosts lack (PHP-9), and the Symfony polyfill would add a runtime dependency to the core (DEP-1). So `scripts/generate-data.php` reads UnicodeData.txt 17.0.0, the NFKC baseline that grammar.md names, and writes `src/Internal/NfkcTable.php`. The table maps each character whose NFKC form holds only ASCII characters and separators to that form, and `Postcode::normalize()` applies it with `strtr()`.

For these characters the table equals NFKC. None of the characters in their decompositions is a combining mark, so nothing in a decomposition composes. A combining mark next to a table character can compose with it in full NFKC, as U+0300 does with the letter A. The composed character is not ASCII. The table leaves the mark in place, and the mark is not ASCII either. `parse` rejects both results as `bad_character`, so `parse` and `isLegacy` give the same result as an SDK with full NFKC for every input. `normalize` keeps every other character as it is, so its result can differ from NFKC for text that holds no postcode, such as the micro sign U+00B5.
